# DealCapital — P2.2 Privacidad de proyectos y notificaciones (2026-11-03)

## Aplicado en Supabase
- Migración **20261103172732_dealcapital_project_column_privacy_event_notifications_20261103** aplicada y guardada en `supabase/migrations`.
- `public.proyectos` ya no concede SELECT general a `anon` ni `authenticated`. Solo pueden leer 24 columnas declaradas públicas; **email**, **documento_pdf**, **pitch_deck_url** y **documentos_url** están excluidas de esas concesiones incluso para una sesión autenticada. RLS sigue restringiendo filas de proyectos no publicados.
- `public.dc_admin_project_document_keys(id)` recupera referencias para consulta administrativa **solo** si `auth.users.raw_app_meta_data.role='admin'` actual; ningún enlace firmado se almacena en proyectos. La función no permite cambiar proyectos.
- `public.notificaciones`: eliminado INSERT desde clientes y permiso UPDATE general; únicamente UPDATE de `leida` para el dueño (mediante RLS).
- Triggers privados crean notificaciones genéricas y sin datos identificatorios a partir de INSERT de `interesados`, INSERT de `mensajes` y cambios válidos de estado de `compromisos`.
- Trigger de compromisos protege identidad del inversionista, proyecto, monto, mensaje y timestamps; solo pasa de `pendiente` a `aceptado` o `rechazado` para propietarios permitidos.
- El navegador ya no escribe directamente notificaciones.
- `/compromisos` ya no incrementa `monto_recaudado` por aceptar compromisos: una intención aceptada NO es transferencia efectiva.

## UI actualizada
- Catálogo, detalle, analítica, favoritos y dashboard: consultas de campos públicos explícitos; se eliminan `select("*")` y joins con `proyectos(*)`.
- Detalle público: no muestra referencias de PDF; los documentos de evaluación son privados.
- Admin: obtiene las referencias privadas bajo demanda mediante RPC autorizada; luego genera enlace de Storage de vida corta.
- Interés, chat y compromisos: los avisos provienen de transacciones del servidor, no de identificadores de destinatario seleccionados en el cliente.

## Pruebas efectuadas
- SQL `BEGIN ... ROLLBACK`: ensayo DDL sin persistencia completado antes de ejecutar migración.
- Concesiones: `anon` no puede consultar `email` ni `pitch_deck_url`; `authenticated` no puede consultar `documento_pdf`; columnas del catálogo permanecen legibles.
- Los usuarios autenticados no pueden INSERT arbitrario en `notificaciones`, ni UPDATE `tipo`, pero sí UPDATE `leida` en su propia fila bajo RLS.
- Simulación `anon`: 4 proyectos publicados visibles; consulta de email denegada.
- `dc_admin_project_document_keys`: consulta autorizada para administrador, rechazada para no administrador.
- Evento de interés: exactamente una notificación, transacción revertida.
- Evento de mensaje con participantes distintos: exactamente una notificación, transacción revertida.
- Evento de compromiso: exactamente una notificación, transacción revertida.
- Los registros de prueba se revirtieron; al iniciar la verificación había 10 proyectos y 23 notificaciones existentes.
- Hay **3 conversaciones históricas con el mismo ID como emprendedor e inversionista**: no se genera notificación a uno mismo. Revisar esos datos; no se modificaron automáticamente.

## Riesgos pendientes
- Los campos de contacto y PDF están ocultos también al propietario mediante SELECT normal. Si desea acceder a referencias ya cargadas, crear función segura de consulta del propio proyecto y una vista privada. La carga y previsualización de PDF al momento de registro ya funcionan por referencia local / URL firmada.
- Las funciones SECURITY DEFINER de revisión/documentos están en el esquema API público por compatibilidad con Supabase RPC, con permisos `EXECUTE` restringidos y validación del rol confiable en `auth.users`; Supabase Advisor emite advertencia para 3 RPC. Evaluar backend server-only para reducir exposición.
- La protección de contraseñas filtradas de Supabase Auth continúa desactivada; activarla en su configuración.
- Queda pendiente E2E de navegador con cuenta real de emprendedor, inversionista, administrador y visitante, y pruebas de revocación de token JWT.
- Las 3 conversaciones históricas de un mismo usuario y los 2 proyectos publicados con estado pendiente requieren revisión manual.
- No mover, borrar o normalizar registros sin auditoría y decisión del responsable.
