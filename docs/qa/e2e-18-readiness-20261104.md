## Requisitos para ejecutar 18/18

1. Crear **un proyecto o rama independiente de Supabase** en la organización correspondiente; comprobar primero si tiene costo por hora/almacenamiento. No crear recursos de pago sin aprobación explícita.
2. Aplicar migraciones/esquema requeridos en ese entorno y generar datos sintéticos; no clonar datos personales desde producción.
3. Configurar un deployment Vercel QA (proyecto separado o entorno con variables de Preview específicas) apuntando al URL y clave pública del Supabase de QA, **no** al de producción.
4. Crear tres cuentas de prueba distintas en ese Supabase; asignar al administrador sintético el rol `admin` en `auth.users.raw_app_meta_data` vía proceso administrativo confiable. El correo del administrador de pruebas debe tener prefijo `qa-`.
5. Configurar un entorno GitHub protegido `qa-staging` con variables `DC_STAGING_BASE_URL`, `DC_STAGING_SUPABASE_REF` y seis secretos: `DC_ENTREPRENEUR_EMAIL`, `DC_ENTREPRENEUR_PASSWORD`, `DC_INVESTOR_EMAIL`, `DC_INVESTOR_PASSWORD`, `DC_ADMIN_EMAIL`, `DC_ADMIN_PASSWORD`.
6. En Actions > `DealCapital QA - authenticated and staging E2E` > Run workflow, ejecutar primero con `run_mutations=false` y después, tras comprobar el backend aislado, con `run_mutations=true`. El pipeline genera archivos JUnit XML; sin `PASSED` los escenarios siguen pendientes.

**Nota:** los dos escenarios de staging dejan registros sintéticos para examinar auditorías; el restablecimiento o limpieza es responsabilidad del entorno aislado.
